# Sales Lessons (Cross-Account)

> 어카운트 간 누적되는 일반화 가능한 인사이트. `/followup`이 매번 추출 시도, 다른 어카운트 `/discovery-prep`과 `/meeting-capture`가 시작 시 참조.
> **개별 어카운트 비밀 정보는 적지 말 것.** 일반화된 패턴만.

## 형식

각 lesson은 다음 형식으로 누적:

```
## L-NNN: [한 줄 lesson 제목]

- **분류**: industry-pattern | persona-pattern | objection-pattern | meeting-pattern | tech-pattern | timing-pattern
- **발견 출처**: [어카운트 이름 또는 "다수 어카운트"] / [날짜]
- **패턴**:
  [어떤 상황에서 어떤 신호가 어떤 결과로 이어지는지 — 인과 또는 상관]
- **활용법**:
  [다음 어카운트에서 어떻게 활용할 것인가 — 어느 스킬에서 적용]
- **반례 / 한계**:
  [이 lesson이 안 통할 만한 케이스 — 과적합 방지]
```

## Lessons (예시 — 실제 lesson이 누적되면 채워짐)

## L-001: 기존 솔루션 갱신 윈도우가 의사결정 트리거다

- **분류**: timing-pattern
- **발견 출처**: KT밀리의서재 / 2026-05-26
- **패턴**: 고객이 이미 동종 솔루션을 사용 중인 경우, 본 계약 의사결정은 기존 솔루션 갱신 협상 시점에 맞춰 일어나는 경향. 갱신까지 9–12개월 이상 남은 시점에 접근하면 "지금은 검토 시점이 아니다"로 deferred 됨.
- **활용법**:
  - `/account-brief`: 기존 솔루션과 그 갱신 시점을 적극 리서치 항목으로 (채용공고, 보도자료, IR 자료에 가끔 노출)
  - `/discovery-prep`: 첫 미팅 SPIN 질문에 "현 솔루션 계약 형태 / 갱신 시점" 검증 질문 1개 포함
- **반례 / 한계**:
  - 신규 카테고리(기존 솔루션 없음)에는 적용 안 됨
  - 페인이 매우 급박한 경우(인시던트, 컴플라이언스 deadline)는 갱신 사이클 무관하게 신속 의사결정

## L-002: 모회사 그룹사 솔루션 정책이 deal-killer 또는 deal-accelerator

- **분류**: industry-pattern
- **발견 출처**: KT밀리의서재 / 2026-06-09
- **패턴**: 대기업 계열사 고객의 경우, 모회사가 "그룹 솔루션 우선" 정책을 강화하면 외부 벤더 deal이 무산되는 경향. 반대로 정책 발표 전에 본 계약을 체결하면 grandfather 적용으로 안전. **타임라인 압박이 deal의 생사**.
- **활용법**:
  - `/account-brief`: 모회사/그룹 차원의 AI/SaaS 정책 동향을 리서치 항목으로
  - `champion-mapper`: watch list에 "그룹 정책 발표 가능성" 항목 의무 체크
  - `/proposal`: 도입 일정에 "정책 발표 전 grandfather 확보" 논리 활용 가능
- **반례 / 한계**: 그룹사가 아닌 독립 고객에는 무관

## L-003: 챔피언 ≠ 친절한 사람

- **분류**: persona-pattern
- **발견 출처**: 일반 원칙 (다수 어카운트)
- **패턴**: 미팅에서 가장 적극적으로 호응하는 사람이 챔피언이 아닐 수 있음. 진짜 챔피언은 (a) 우리 솔루션 성공이 본인 OKR/KPI와 직결되고, (b) 내부 의사결정자에게 우리를 적극 옹호할 의지가 있음.
- **활용법**:
  - `champion-mapper`: 챔피언 라벨링 시 "OKR 직결성" + "내부 옹호 시그널" 명시 요구
  - `/discovery-prep`: Discovery 질문에 "이 프로젝트가 본인 부서/팀의 어떤 지표와 연결되나요?" 포함
- **반례 / 한계**: 신규 부서 신설 직후엔 OKR이 정의되지 않은 상태 — "본인이 부서 OKR을 정의하는 위치인가" 추가 확인 필요

## L-004: 평가/운영 인력 부재가 두 번째 페인으로 등장한다

- **분류**: meeting-pattern
- **발견 출처**: KT밀리의서재 / 2026-06-09
- **패턴**: 1차 미팅(discovery)에서는 기술/제품 페인이 주로 드러나지만, demo 미팅에서 "본 도입 후 운영을 누가 어떻게 할 것인가" 페인이 신규 발견되는 경향. 이 페인이 본 계약 블로커가 되는 경우가 자주 있음.
- **활용법**:
  - `/discovery-prep`: 1차 미팅 SPIN에 운영/평가 인력 질문 1개 선제 포함
  - `meeting-synthesizer`: PoC scope에 "운영 단계 페인 발견 시 대응" 미니 섹션 포함 고려
  - `proposal-writer`: 운영 자동화/도구 마일스톤을 본 계약 약속에 포함하는 패턴
- **반례 / 한계**: API-only / fully-managed 서비스는 고객 측 운영 부담이 적어 이 패턴 약함

## 추가 규칙

- **5개 이상 사례가 누적되기 전까지 lesson으로 등록 금지** (단일 사례는 anecdote, 패턴이 아님)
  - 예외: 위 L-001 ~ L-004는 일반 영업 이론에서 검증된 원칙이라 초기 시드로 등록
- **신규 lesson 등록 시 반드시 "반례 / 한계" 채울 것** — 과적합 방지
- **분기마다 한 번 리뷰**: 안 쓰이는 lesson 삭제, 새 패턴 promote
