# Review Notes — PR #150

## Code Review
_Source: reviewer-degraded_

- **[High] A non-zero exit with ZERO attributed failures is certified as RED — a project with --cov-fail-under in addopts now passes the RED gate unconditionally (regression)**
  Evidence: scripts/verify_checkpoint.py:771-783 — after the 124/4/5 refusals, ANY non-zero exit prints 'PASS: RED phase — the branch's own tests fail as expected'. `_failed_test_files` has already returned [] (no in-scope file was blamed) and that evidence is discarded for the verdict. Decisive probe (probe repo: lib.py fully covered by the existing suite, addopts = "--cov=lib --cov-fail-under=50", branch test `assert True` i.e. PASSING): whole-suite child run -> 'Required test coverage of 50% reached. Total coverage: 100.00% / 2 passed'; scoped child run -> 'FAIL Required test coverage of 50% not reached. Total coverage: 0.00% / 1 passed', exit 1. Real consumer, same worktree: PRE-FIX (main kit) 'FAIL: RED phase — tests passed but should fail before implementation.' exit=1 (CORRECT refusal); POST-FIX (branch kit) 'PASS: RED phase — the branch's own tests fail as expected (exit 1) — scope was tests/test_branch_feature.py (per-file attribution unavailable from pytest's output)' exit=0 (WRONG). Two further reproductions of the same root: (a) pytest module absent -> 'No module named pytest', exit 1 -> 'PASS: RED phase ... (exit 1)' exit=0, nothing ran at all; (b) JS project whose package.json test script is 'echo JS-RUNNER-INVOKED; exit 1' (executes zero tests) -> 'PASS: RED phase — the branch's own tests fail as expected (exit 1)' exit=0, because the JS branch sets no_run_codes = () at scripts/verify_checkpoint.py:736 so NONE of the 'evaluated nothing' refusals apply to JS, although the hazard note at lines 715-720 claims that route is closed.
  Fix: Do not treat a bare non-zero exit as proof that a branch test failed. Minimum: when the runner is pytest and `_failed_test_files` attributes nothing AND the output carries no 'N failed'/'N error' summary, refuse as inconclusive instead of certifying RED. Also neutralise the consumer project's reporting/coverage addopts for the scoped run (the run is a probe, not a quality gate) — e.g. add `-p no:cacheprovider --no-cov` or `-o addopts=''` and keep the explicitly chosen flags. Give the JS branch a usage/no-run refusal too rather than an empty no_run_codes. Note this is a design decision, not a one-liner: a blanket 'require attribution' rule would also refuse the legitimately-unattributable rootdir-differs case the PR deliberately degrades, so the two must be distinguished.

- **[High] The new 'cannot compute the branch's test-file delta' refusal is masked by any untracked test file, and untracked paths are the gate's executable subject**
  Evidence: scripts/verify_checkpoint.py:680-695 — the uncomputable-base guard is nested INSIDE `if not all_test_files:`, so it is consulted only when the delta is already empty. Probe A (repo whose default branch is 'trunk', so base 'main' does not resolve; helper state measured as default_branch=main, merge_base=None, changed=[]): 'FAIL: RED phase — cannot compute the branch's test-file delta: no merge-base with 'main' and 'main' does not resolve in the worktree — inconclusive, and NOT the same as 'no tests were written'' exit=1 (correct). Probe B, the IDENTICAL worktree plus one untracked tests/test_stray.py containing `assert False`: 'PASS: RED phase — the branch's own tests fail as expected (exit 1) — failing: tests/test_stray.py' exit=0. The gate asserts the file is 'the branch's own' while the branch delta is provably unknown. Probe C (base resolves normally; committed branch test passes; stray untracked tests/test_scratch.py fails): 'PASS: RED phase — the branch's own tests fail as expected (exit 1) — failing: tests/test_scratch.py' exit=0 — a scratch file alone certifies RED while every committed branch test is green. Review lesson 5 (workspace state a gate reads is untrusted input — validate on read) and the computed-and-empty vs could-not-compute rule; also lesson-12-shaped, in that the check sits where the condition it guards can bypass it.
  Fix: Evaluate the uncomputable-base check BEFORE trusting the delta, not only when the delta is empty, so 'could not compute' cannot be overwritten by whatever happens to be lying in the worktree. Separately, mark untracked members of the scope in the rendered output (e.g. 'tests/test_stray.py (untracked)') so an implementer can see what the gate actually judged. Do NOT restrict the subject to tracked paths: during a genuine RED the new test file is routinely still untracked, so that would break the primary flow. The PR body's disclosure ('an untracked stray test file ... accepted — pre-existing property of the shared helper, unchanged here') understates this: the helper is unchanged, but post-fix untracked paths became the EXECUTED subject and can single-handedly certify RED, and they also mask a refusal this PR newly added.

- **[Medium] The one deliberately-changed legacy behaviour (pytest exit 5) ships with no AC of its own, and its documented worked example does not reproduce on the shipped pytest**
  Evidence: scripts/verify_checkpoint.py:715-718 (the hazard note, which is AC-4's own subject) states as measured fact: 'both measured as reachable through the SCOPED path, e.g. a branch whose only changed test file is `tests/conftest.py`'. tests/test_red_gate_scoping.py:367-371 repeats it: 'A branch whose only changed test file is `tests/conftest.py` collects zero cases (measured: exit 5)', and the PR body's table says that case is 'collects zero cases -> pytest exit 5 -> refused as inconclusive'. Measured on pytest 9.0.3 (this repo's dev extra): `python3 -m pytest -q --tb=short -rfE tests/conftest.py` -> '1 passed', child_exit=0 — pytest DOES collect test functions from an explicitly named conftest.py. Real consumer on a conftest-only branch: 'FAIL: RED phase — tests passed but should fail before implementation. / The branch's own tests all passed: tests/conftest.py' exit=1 — the exit-0 branch, not the exit-5 inconclusive branch. The guard itself is live and the change is correct: reached via a different route (a test file whose only `def test_` is inside a comment, which `_has_real_tests`' content regex accepts), POST-FIX gives 'FAIL: RED phase — pytest evaluated none of the branch's own tests (exit 5: nothing collected / usage error) — inconclusive' exit=1 versus PRE-FIX 'PASS: RED phase — tests fail as expected (exit 1)' exit=0. Review lesson 14: work added to satisfy a request for a DECISION shipped without acceptance criteria, and that is where the defect is — in the justification, not the code.
  Fix: Keep the behaviour change (it closes a fail-open the pre-existing comment itself called a fake RED pass), but give it its own AC in ISSUE-103 so the decision is recorded and disarm-tested as a first-class requirement. Replace the conftest-only example in the hazard note, the test docstring and the PR body with the route that actually reproduces on pytest 9.x, or state the pytest version the conftest claim was measured on and that it no longer holds.

- **[Medium] _failed_test_files scans the whole output stream rather than pytest's summary section, so it names a PASSING in-scope file as failing**
  Evidence: scripts/verify_checkpoint.py:619 and 637-643. The docstring states the oracle is 'pytest's "short test summary info" section', but `_PYTEST_SUMMARY_RE.findall(output)` is applied to all of stdout, which under `--tb=short` includes each failing test's captured stdout. Probe: tests/test_liar.py does `print('FAILED tests/test_victim.py::test_v - forged')` then fails; tests/test_victim.py passes. With scope ['tests/test_liar.py', 'tests/test_victim.py'], `_failed_test_files` returned ['tests/test_victim.py', 'tests/test_liar.py'] — the PASSING file is attributed, and listed first. Review lesson 4: a hand-rolled parser must match the oracle's intended BOUNDARY, not just its line format; lesson 6: a text shape is not provenance. Impact is diagnostic only — the verdict is driven by the exit code, so this cannot flip the gate — which is why it is Medium and not High.
  Fix: Slice the output at the '=== short test summary info ===' header and match only below it, or require the captured nodeid to be followed by ' - ' or end-of-line AND appear after the summary header. Add a both-directions guard: a forged in-scope 'FAILED ...' line printed from a test body must NOT be attributed, while the genuine summary line must be.

## Security Findings
_Source: reviewer-degraded_

- **[Low] Scope paths (including untracked, filename-controlled ones) are interpolated into the runner argv with no leading-dash guard; fails closed for pytest, fails OPEN for the JS branch**
  Evidence: scripts/verify_checkpoint.py:735 and 740 build `cmd` by splatting `*scoped` into the argv. `scoped` derives from `_changed_files_vs_base`, which includes `git ls-files --others` output, so repo filenames decide argv content. There is no command injection: `_run` calls `subprocess.run` in list form with no `shell=True` (scripts/verify_checkpoint.py:44), so this is argument injection only. A path that begins with '-' (reachable as e.g. '-d/tests/x.py', which `test_dir_pattern` matches) is parsed by the child as an option. For pytest that produces exit 4, which the new `no_run_codes` refusal catches — fails closed. For the JS branch `no_run_codes = ()` (line 736), so a runner usage error is non-zero and is certified as 'PASS: RED phase'. Verified clean in the same pass: no secrets or credentials added (the only regex hit in the diff is the test name `test_mid_line_failed_token_is_not_a_summary_line`); no new dependency (the diff touches exactly 2 files, neither of them pyproject.toml); no new env knob (the only `os.environ` line added is the test helper filtering CLAUDE_PLUGIN_ROOT, so review lesson 2 has nothing to document). ReDoS cleared by execution, not by reading: the shipped `^(?:FAILED|ERROR)\s+(\S+)` pattern (printed back during the probe to confirm the real object was exercised) ran 100k-space, 1M-char, 50k-line and no-match 1MB inputs in 0.10/2.28/9.17/4.06 ms — linear, no catastrophic backtracking.
  Fix: Insert the pytest `--` separator (or prefix each path with './') before splatting scope paths, and give the JS branch a usage-error refusal so an option-parse failure cannot read as RED. No exploit path to code execution, so this is a gate-integrity hardening item rather than a vulnerability.
