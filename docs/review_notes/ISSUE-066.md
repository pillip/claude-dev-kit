## Security Findings
_Source: reviewer-degraded_

- **[Medium] The run-id whitelist's fullmatch ANCHORING is unpinned — fullmatch->match survives the whole suite, and the mutant writes outside the project**
  Evidence: tests/test_review_context.py:320-335 is the only invalid-run-id test and its single vector is `../evil`, which a prefix-anchored `re.match` also rejects, so mutating `_RUN_ID_RE.fullmatch` to `.match` at scripts/review_context.py:161 survives 44/44 tests. Against that mutant, `KIT_RUN_ID='sub/../../../../SENSITIVE'` wrote `SENSITIVE.jsonl` OUTSIDE the project: the containment check at :166 cannot catch it because it validates `runs_dir` before the run id is appended as the filename. The SHIPPED code is safe — independently re-verified: that exact vector against the unmutated module writes nothing and leaves the runs dir empty. This is a test-coverage gap, not a live vulnerability, and it matters most because ISSUE-067's rebase replaces precisely this function body.
  Fix: Add one vector with a VALID prefix and an invalid tail (e.g. `sub/../../../../SENSITIVE`) and assert the raw value never appears as a path component anywhere under the fixture root. Carry the vector into tests/test_kit_telemetry.py TC-067d at the rebase, since that is where the control will then live.

- **[Medium] The unset-KIT_RUN_ID absence assertion hollow-passes: _no_events probes a fixed filename, so a loosened whitelist writes a stray file with a green suite**
  Evidence: tests/test_review_context.py:75-76 defines `_no_events` as `not (runs / f"{run_id}.jsonl").exists()`. Mutating `_RUN_ID_RE` from `{1,64}` to `{0,64}` makes the empty run id valid, so every unconfigured run appends to `.claude/runs/.jsonl` — and `test_unset_run_id_is_silent_noop_exit_0`:304 still passes because it only checks for `testrun.jsonl`. The sibling test at :327 already uses the correct form (`list((project / ".claude" / "runs").iterdir()) == []`).
  Fix: Make `_no_events` enumerate the directory rather than probe one name, so every absence assertion in the file catches writes at unexpected filenames (review lessons 3 and 4).

- **[Low] Unbounded _ISSUE_ID_RE combined with issue_id sitting OUTSIDE the truncation loop silently drops the whole forensic event**
  Evidence: scripts/review_context.py:90 (`ISSUE-\d+`, no length bound) and :178-180, where `issue_id` is assigned after the `trimmed` loop at :169-172 and so is never truncated. A ~4090-digit issue id therefore pushes the serialized event past `_MAX_EVENT_BYTES` and the 4096-byte cap drops it entirely (verified: 0 JSONL lines) — the opposite of the PR's own truncate-don't-drop control, which tests/test_review_context.py:394 pins for payload values only. Main's baseline defends the analogous field with a bounded `_GATE_NAME_RE {0,63}`. Max impact is a lost best-effort event; the id never reaches a path or a shell.
  Fix: Either bound the regex (`ISSUE-\d{1,8}`) or move the `issue_id` assignment inside the truncation loop.

- **[Low] The closed-vocabulary ValueError guard is real but surfaces as a traceback/exit 1, not the documented exit 2, for direct Python callers**
  Evidence: scripts/review_context.py:120-124. Mutation-verified as load-bearing (removing it fails a test, so the guard is not argparse-only). It is unreachable from the CLI because argparse `choices` rejects first; a library caller gets an uncaught ValueError while the module docstring at :52-53 documents "2 = bad input (closed-vocabulary violation...)".
  Fix: Either catch ValueError in `main` and return 2, or scope the docstring's exit-code claim to the CLI boundary.
