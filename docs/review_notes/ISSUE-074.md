## Security Findings
_Source: reviewer-degraded_

- **[High] RESOLVED in review (c9453dd) — the prescribed bash -c handoff corrupts the registry on an apostrophe, under the lock, with no error**
  Evidence: Both contracts prescribed `bash scripts/registry_edit.sh issues.md -- bash -c '<apply script>'`, and the issue's own Implementation Notes call byte-exactness "the real design question in fix 2". Independently verified by tokenizing the contract's own form: with the title "### ISSUE-077: Don't drop the user's draft", shlex yields 10 tokens instead of 7 and `bash -c` receives only "grep -q ... || cat >> issues.md <<EOF\n### ISSUE-077: Dont" — the quote closes at Don't, the heredoc delimiter is lost, and the remainder ('drop', 'the', "users draft\nEOF") leaks into positional args. Bash warns but still runs the `cat`, appending a TRUNCATED block while holding the lock. Apostrophes are near-certain in issue titles and ACs, so this is ordinary content, not an adversary. Chains with the idempotence guard: the truncated anchor then satisfies the guard on every retry, so the issue is never written and nothing ever errors — the precise ISSUE-074 signature reproduced inside its own replacement mechanism.
  Fix: Applied: both contracts now mandate a quoted heredoc (`<<'KIT_EOF'` … `KIT_EOF`) and forbid interpolating a bare apostrophe into the single-quoted argument; the same rule is stated at the new skill-layer receiver. The anchor guard must now match line-anchored (`^### ISSUE-NNN:`) and ANNOUNCE its no-op on stderr, so a dropped write stays attributable. Residual recorded below: the string form is still the prescribed shape.

- **[Medium] OPEN — fix 2 grants the planner shell by deputy: planner-authored text becomes the committer's bash -c payload, bounded only by prose review**
  Evidence: Nothing in either contract constrains the apply script's CONTENT — no grammar, no allowed-command set, no target-file restriction. Because flock_edit.sh executes its argv verbatim ("$@" at :29 and :83) the script runs with the committer's full Bash and can touch scripts/, .github/workflows/, anything; the `issues.md` in the command names only what gets LOCKED, not what gets WRITTEN, so the invocation reads far narrower than it is. The sole control is "team-lead reviews the script's content before running it" — an LLM reviewing LLM-authored shell, with no test or validator behind it. Planner inputs include the PRD and, in /scan evidence mode, scanned repository content, so the realistic vector is indirect prompt injection reaching a privileged shell. On review lesson 6: the contract's provenance disclaimer ("shape validation is not provenance, so the committing actor is accountable") is honest and does not launder the risk as a guarantee, but it assigns accountability rather than bounding the payload.
  Fix: Bound the payload instead of reviewing it: the planner already holds Write, so have it emit the apply script to a scratch file and have the committer run a fixed `-- bash <script-path>` (which also removes the quoting hazard entirely). Both review dimensions independently recommended this. Deliberately NOT applied: the issue prescribes "planner-authored idempotent apply scripts ... run by a Bash-capable caller under registry_edit.sh" as the handoff shape, and replacing the string form with a file-and-scratch-dir convention is a design change plus a new repo convention — a planner decision, and the natural companion to the non-exec'ing content-only wrapper the issue already records as the follow-up path. Needs a follow-up issue.

- **[Medium] OPEN — the anchor-presence idempotence guard can still no-op on an incomplete block, and the unanchored-match class is live**
  Evidence: Line-anchoring and the stderr announcement were added in review, but the guard still has no COMPLETENESS check: an anchor left by a partial prior write satisfies it, so the script no-ops forever and the half-written block can never self-repair. On the unanchored-match class: the live 466 KB issues.md already carries 8 non-heading `### ISSUE-NNN` occurrences — 6 machine-generated `<!-- ### ISSUE-0NN SHIP NOTE -->` comments (lines 3602, 3662, 3719, 3772, 4031, 4243) and 2 prose citations (4198, 4212) — verified independently. Today's colon saves the specific match (the SHIP NOTE comments carry no colon), so this is a latent class risk rather than a live bug, and the line-anchoring added in review now closes it. Credit: the guard runs INSIDE the lock (the whole script is the bash -c argument), so it is TOCTOU-free — but the contract still does not say WHY, so a future refactor could hoist it out.
  Fix: Require the script to verify the block is complete (anchor AND its terminating `---`) before deciding to no-op, and state in the contract that the guard must run inside the lock. Needs a follow-up issue.

- **[Low] CONFIRMED (GAP-074b, already carried) — three STATUS.md steps instruct updating a file this repo must not gain, and "update" creates it here**
  Evidence: agents/issue-writer.md:34, agents/team-lead.md:119 and agents/team-lead.md:216 — note the third is :216, not the :214 recorded in the carrier; team-lead's line numbers shifted by this PR's +8. Capability is fine (both actors hold Bash) and all three are "update" forms, so AC-6 passes. The defect is that update CREATES here: flock_edit.sh:30 opens 200>"$LOCKFILE", unconditionally creating STATUS.md.lock, and any `cat >>`/`cat >` update command creates STATUS.md itself. The skill layer is worse and is outside the agent-only sweep: skills/kickoff/SKILL.md:145 and skills/scan/SKILL.md:126 both say "Create/update STATUS.md" outright. Correct that issue-writer.md:34 is absent from the issue's own Out-list audit.
  Fix: Fold in the same conditional scoping planner step 6 now uses, and extend it to the two skill-layer sites. Already carried as GAP-074b at docs/test_plan.md:477 — add the :214 -> :216 correction and the two skill sites to that carrier.

- **[Low] Standard security sweep — clean; and the issue's rejection of fix 1 is independently confirmed sound**
  Evidence: No secrets, no dependency changes, no new network or filesystem surface, no path traversal (KIT_ROOT is derived from __file__ and every agent path comes from AGENT_DIR.glob or a literal — no external input reaches a path). The arbitrary-code-execution basis for rejecting fix 1 is ACCURATE, verified from source: flock_edit.sh takes TARGET="$1", requires a literal `--`, then executes the remaining argv verbatim at :29 and :83 with no allowlist and no restriction to bash; registry_edit.sh:30 forwards everything via `exec bash ... flock_edit.sh "$ROOT/$FILE" "$@"`; and the documented usage at registry_edit.sh:9-10 is literally `-- bash -c '<update command>'`.
